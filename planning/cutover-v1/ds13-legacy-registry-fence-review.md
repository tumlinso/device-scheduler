# DS-13 legacy registry fence review

**Disposition:** A directory at the exact legacy SQLite filename is a useful, fail-closed compatibility fence for old code that still calls `sqlite3.connect()` without the newer Project Control authority selector. The cutover is not proven by this source/configuration review: I did not inspect the live database, processes, descriptors, services, or GPUs.

Project Control's current coordinator resolves `PROJECT_CONTROL_HOST_RESOURCES_RUNTIME_DIR`, then `TODO_BACKGROUND_HOST_RUNTIME_DIR`, then an owned `$XDG_RUNTIME_DIR/codex-todo-orchestrator`, and finally the temp-directory default; it opens `physical-resources.sqlite3` and enables WAL on writes ([coordinator.py](/home/tumlinson/project-control/src/project_control/host_resources/coordinator.py:70)). The source coordinator checks the DS selector before opening SQLite, but the legacy implementation has no such check and creates the database if missing ([legacy host.py](/home/tumlinson/project-control/legacy/todo_orchestrator-reference/background/host.py:65)). Current deployed HTTP and inference units and the installed launcher point at `/tmp/codex-todo-orchestrator-1000`; the candidate verification unit instead points at `%t/codex-todo-orchestrator` ([user service](/home/tumlinson/.config/systemd/user/project-control.service:8), [inference service](/home/tumlinson/.config/systemd/user/project-control-inference.service:8), [candidate template](/home/tumlinson/project-control/deployment/project-control-candidate.service:7)). Thus the proposed fence blocks the canonical path only; an old binary launched with another root can recreate a separate registry.

Before replacing `/tmp/codex-todo-orchestrator-1000/physical-resources.sqlite3` with a directory:

1. Hold the exclusive DS-13 cutover gate; verify legacy admissions are fenced, every old owner/reservation/intent is reconciled or transferred, NVIDIA resources are idle, and DS is ready to become the only allocator. A zero GPU-process count alone does not establish zero registry ownership.
2. Stop both Project Control HTTP and inference units, plus any old CLI/stdio/worker process that can use `HostCoordinator`. Verify the old service cgroups are empty and scan open descriptors for the database, `-wal`, and `-shm` files (including unlinked/renamed inodes) before moving anything. A process with an already-open SQLite handle bypasses a pathname tombstone. `KillMode=control-group` helps for unit children, but does not cover separate clients.
3. Resolve and record every reachable legacy runtime root and selector root, including `PROJECT_CONTROL_HOST_RESOURCES_RUNTIME_DIR`, `TODO_BACKGROUND_HOST_RUNTIME_DIR`, `XDG_RUNTIME_DIR`, and `XDG_CONFIG_HOME`. Keep all legacy-capable entrypoints pinned to the exact canonical runtime root and do not start the candidate-verification unit with its `%t` alternate root. The production unit's current explicit `TODO_BACKGROUND_HOST_RUNTIME_DIR` is evidence for the intended path, not proof of every process's environment.
4. Back up the database using SQLite's backup API to a private, durable location outside `/tmp`; run an integrity check and record the backup receipt before proceeding. Because writers set WAL mode, do not copy only the main `.sqlite3` file. After all handles are gone, checkpoint/close cleanly or preserve the main file and any remaining WAL sidecars together. Rename the original on the same filesystem, then create the directory at the exact old database path with a `RETIRED` marker. Keep old callers stopped through the file-to-directory transition; the two filesystem operations have a brief missing-path interval in which legacy code could recreate the DB.
5. Start DS, select DS in Project Control, activate the new immutable candidate, and restart the production HTTP unit using the established sealed-release procedure. Verify candidate identity/readiness, successful DS-backed owner queries, and that the canonical tombstone remains a directory and no SQLite file reappears. Keep inference demand-only unless separately authorized.

The cutover contract already requires reconciliation, a single-authority audit, and rollback materials ([cutover README](README.md:11), [DS-13 acceptance](/home/tumlinson/device-scheduler/planning/implementation-plan.json:1210)). The `/tmp` tombstone is a live-cutover guard, not durable reboot protection; preserve the backup and retirement record outside `/tmp`. Rollback must retain one allocator at a time: do not restore local authority or reopen the old DB while DS still owns that pool.

**Coverage limit:** Source and unit files were re-read; the DS-13 task was checked through Project Control at semantic revision 36. The live DB's existence, WAL state, resolved environment roots, descriptor census, unit activity, actual candidate identity, and runtime owner counts remain unverified and must be checked at the authorized cutover.
